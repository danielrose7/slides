Plantiful · Sales Tax v2 (Avalara +)

Architecture

How Plantiful connects to Avalara: the account model, per-org companies, nexus sync, the client layer, and call persistence.

Account & company model

Plantiful Avalara account (credentials: accountId + licenseKey, server-side env)
├── Company "org-a" (companyCode, nexus declarations, locations)
├── Company "org-b"
└── ... one per organization with the Avalara entitlement
  • One Plantiful account per environment. Sandbox (sandbox-rest.avatax.com) and production (rest.avatax.com) are fully separate credential worlds. One license key per account per environment; regenerating instantly revokes the old key for every org — rotation is a single coordinated swap, plan ops accordingly.
  • One Avalara company per organization, provisioned programmatically via the Companies API when a Plantiful employee enables the org's Avalara entitlement. companyCode is caller-chosen, max 25 characters, and must be a short stable org identifier. The binding lives on an org ↔ Avalara foundation record (IntegrationLink analog): org FK, companyCode, provisioning status, entitlement flag.
  • Org admins never see Avalara credentials. The entitlement is internal-admin only; the org-admin-facing surface is the auto-calc setting, which is hidden entirely when the entitlement is off.
  • Re-enabling an org reuses its existing company; disabling preserves the binding and short-circuits all transactional calls.

Nexus: registration syncs to Avalara

Avalara returns $0 for any jurisdiction where the company has no declared nexus ("If you do not declare any nexus, your account will not calculate any tax!"). Registration therefore cannot live only in Plantiful:

  • The org's sales-tax registration config (states; sub-state jurisdictions in home-rule states like AL/CO/LA/AK) is edited in Plantiful and is the source of truth.
  • On save, Plantiful mirrors the config to the org's Avalara company as nexus declarations (create/remove via API).
  • Home-rule specifics (endpoint shapes for local declarations; whether declaring a subset of locals natively scopes the calculation) are determined during the registration implementation. If native scoping holds, no response-side authority suppression is needed in the engine.
  • The engine's "is the destination registered?" pre-check is a cost optimization (skip a billable call that would return $0), not the compliance mechanism — Avalara's nexus handling is.

Client layer

src/server/utils/avalara/ mirrors the Rutter client layout (src/server/utils/rutter/).

  • SDK: official avatax npm package (AvaTax-REST-V2-JS-SDK) unless evaluation surfaces a blocker.
  • Credential resolution from Plantiful-account-level env config; companyCode resolution from the org's foundation record.
  • Entitlement short-circuit: transactional calls are refused when the org's entitlement is off. Lookup endpoints stay callable but bill at ~1/10 the transaction rate — cache lookup results (tax codes, jurisdiction lists) server-side; never call per keystroke.
  • X-Avalara-Client header on every call (required for all integrations): Plantiful;a0nUz0000158kdYIAQ (app name + Avalara-issued version value). The exact sandbox vs production variants need confirming with Avalara — kickoff notes mention a QA suffix off-production, but the recorded value doesn't end that way. The SDK auto-fills adapter fields.
  • Connection reuse: SSL negotiation costs ~0.22s per round trip; keep-alive is mandatory, not optional.
  • Expose CreateOrAdjustTransaction in the client surface — it is the idempotent retry primitive for persisted document types (see error handling).

Call persistence: AvalaraCallRecord

Every AvaTax request/response persists via an AvalaraCallRecord model (AccountingSyncRecord analog): org FK, shipment/order FKs, request pathname/method/body, response body, status, initiatedAt, Avalara document identifiers. Written at the client layer so persistence is automatic, not per-feature opt-in. The record is created before dispatch with the request payload; the response — or the failure — lands on the same row, so a timeout can never produce a response-only or missing record.

Because request/response bodies carry end-customer PII (names, addresses, exemption certificates), the store needs guardrails from day one:

  • Org-scoped access — reads always filter by organizationId; no cross-organization query surface.
  • Retention — define a bounded window (e.g. keep raw bodies N months, then prune or truncate to summary fields); decide before launch, not after the table grows.
  • Redaction — the admin log-viewer surface (future) masks certificate numbers and anything not needed for debugging.

This one table serves four consumers: the sales-order tax display, error debugging (full request+response even when the user proceeds manually), the per-shipment per-jurisdiction breakdown (parsed from stored responses — never recomputed), and the outage-reconciliation pattern (replay the saved payload with a TaxOverride).

Billing model

Call class Rate Gated by entitlement?
SalesOrder calculations (v1 default) ~1/10 transaction rate Yes
Committed/invoice documents (future) Full transaction rate Yes
Lookups (ListTaxCodes, jurisdictions, ResolveAddress) ~1/10 transaction rate No — but cache aggressively

Sandbox usage is not billed. Per-org cost control = the entitlement gate + the registered-destination pre-check + debounce (see calculation flow).

Data split: Avalara company vs Plantiful

Lives on the Avalara company Lives in Plantiful
Nexus declarations (mirrored from registration config) Registration config (source of truth)
Location codes per POS facility (+ addresses) Org locations, facility addresses
— Tax classification ↔ tax code mapping (constants)
— Exemption reason ↔ entity/use code mapping (constants)
— All calculation results (AvalaraCallRecord, per-jurisdiction breakdown)

Nothing org-specific is configured through Avalara's UI; the admin console is a Plantiful-internal debugging surface only.
