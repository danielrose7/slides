Plantiful · Sales Tax v2 (Avalara +)

Document lifecycle

Avalara document types, the v1 calculator-only lifecycle, returns and corrections, and the migration path to committed transactions.

Avalara's document model (background)

Four transaction families × two lifetimes:

Family Temporary (estimate) Permanent (recorded)
Sales SalesOrder SalesInvoice
Return ReturnOrder ReturnInvoice
Purchase PurchaseOrder PurchaseInvoice
Inventory transfer InventoryTransferOrder InventoryTransferInvoice
  • "Order" types are never persisted: id -1, unfetchable, never reportable, nothing to cancel. "Invoice" types persist even uncommitted (excluded from reporting until committed).
  • Statuses for persisted docs: Saved → Posted → Committed → (filing approval) Locked. Locked, not Committed, is the immutability boundary — committed docs can still be adjusted or voided until a filing locks them.
  • Duplicate docCode on CreateTransaction is an error, never an upsert; the update path for persisted docs is AdjustTransaction (or the CreateOrAdjustTransaction upsert).
  • Never use the Purchase family (consumer-use tax semantics) — seller-side only.

v1: calculator-only

Every v1 calculation is DocType: SalesOrder:

  • ~1/10 the cost of committed transactions.
  • Abandonment, deletion, and voiding in Plantiful are no-ops toward Avalara — nothing was recorded.
  • Nothing Plantiful sells is reported to any tax authority through Avalara in v1; filing remains the org's own process (informed by the per-jurisdiction breakdown we store).
  • Recalculation = a fresh SalesOrder call; there is no server-side state to keep in sync.

The tax basis can change (and recalculates) at any point until the invoice is fully paid.

The fully-paid boundary

"Post-paid" means fully paid, not partially paid:

  • Partially paid orders recalc normally — the tax basis is still live.
  • Fully paid invoices cannot receive new credits in Plantiful (that would require voiding a payment first). Money coming back on a fully paid order is therefore always a return/refund, never a credit-driven recalc.

Returns & corrections

Two mechanisms, split by intent:

  • Return (goods/money back to the customer): a return document with
    • TaxOverride: TaxDate = the original sale's tax date (historical rate applies),
    • docDate = the date the return was made,
    • positive quantity + negative amount per returned line, returned lines only.
    • RefundTransaction automates exactly this (Full / Partial / TaxOnly / Percentage) — evaluate using it directly.
    • Avalara stores no link between a return and its original invoice; Plantiful persists that linkage.
  • Small correction (fixing a mistake on an existing order): adjustment semantics (AdjustTransaction territory in the commit era; in v1, often just a recalc since nothing is recorded).

Open design line to draw: the precise boundary between "return" and "correction" — e.g. any quantity coming back is a return; a price fix on a line is a correction.

⚠️ OPEN DECISION — v1 return doc type. ReturnInvoice is a persisted type, which conflicts with the "every v1 call is unrecorded" settled decision. The two candidate resolutions: (a) v1 returns use the temporary ReturnOrder for calculation only — fully consistent with calculator-only, nothing recorded; or (b) returns become the one persisted-document exception in v1 — which pulls void handling, replay, and idempotency into v1 scope. Until the returns ticket resolves this, treat the SalesOrder-only decision as carrying this single flagged exception. Do not build on either assumption.

Migration path to committed transactions (future phase)

  1. Finalization trigger: invoice reaches fully paid → create/commit a SalesInvoice (via commit: true or CommitTransaction). Recalculate at commit time — never trust a stale estimate.
  2. docCode continuity: an invoice may reuse the estimate's docCode (Order types are unrecorded, so no collision), subject to the verified uniqueness key.
  3. Amendments: committed-but-unlocked docs adjust/void; locked docs take a compensating ReturnInvoice only.
  4. Voiding: canceled/archived sales void their committed transaction (DocVoided/DocDeleted).
  5. Nexus is already declared per company in v1 (calculation requires it), so the commit era inherits a correct tax profile — no nexus migration needed.
  6. VerifyTransaction supports nightly ledger reconciliation (assert date/totalAmount/totalTax against our records) if wanted.
