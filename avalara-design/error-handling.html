Error handling & resilience

Error taxonomy, retry/idempotency, what users see, and the outage playbook.

Two error classes

  1. AvaTax errors — structured JSON with an error code. Avalara writes these for end-user consumption: show code + message verbatim on the sales order page, with category-specific hints. Errors and Exceptions share one handling path (Avalara's explicit guidance). "Verbatim" means verbatim content, escaped rendering: message values render as plain text (never dangerouslySetInnerHTML), bounded in length — external error strings are untrusted input, not markup.
  2. OS/network errors — timeouts, dropped connections. Trap them; never expose a raw exception to the user. Set an explicit client-side timeout (interactive web app ⇒ short). ForceTimeout ($include=ForceTimeout, 30s server delay) is the purpose-built test hook for this path.

Address "deliverable but imprecise" outcomes are messages, not top-level error codes — the fix-address UX reads the messages array, not just the code.

Retry & idempotency

  • v1 SalesOrder calls are unrecorded — retries are inherently safe.
  • Persisted document types (returns; the commit era): a timed-out create may have succeeded server-side, and re-POSTing the same docCode errors (DocumentCodeConflict). Retry via CreateOrAdjustTransaction — an upsert by docCode that is correct whether or not the original landed. Always send our own docCode; omitting it (server-assigned GUID) forfeits this protection.
  • Open a fresh connection for the retry attempt (Avalara's guidance).

User-facing failure path

When a calculation fails and retry doesn't resolve it:

  1. The order cannot save with auto-calculated tax until the error resolves or the user explicitly proceeds manually.
  2. Manual proceed defaults to $0 tax with the option to enter an amount. Every manual proceed is logged (who, when, which error) — admins can see which orders bypassed Avalara.
  3. POS: failures surface but never block checkout. Open question (POS ticket): what tax amount applies when the calculation fails at checkout — last successful estimate for this cart, a configured fallback, or $0? Whatever the answer, the choice is logged with the failed calculation so under-collection is auditable and reconcilable.

Note: Avalara's own outage guidance never endorses "proceed at $0 and forget" — its sanctioned strategies are block-completion or estimated-rate-then-reconcile, under the cardinal rule whatever you collect, you must remit. Our manual-proceed path is an operator escape hatch, deliberately logged and visible, not a silent default.

Outages

  • Avalara does not queue transactions — any queue/replay layer is ours (Inngest).
  • v1 posture: tax estimates fail visibly; the manual path covers urgent orders; recalculation happens organically on the next tax-basis change or manual flush once service returns. Nothing needs replaying because nothing is recorded.
  • If a fallback/manual tax was charged on a persisted doc (commit era), the documented reconciliation: replay the saved CreateTransactionModel (from AvalaraCallRecord) with TaxOverride: TaxAmount via CreateOrAdjustTransaction. The response then carries both totalTax (charged) and totalTaxCalculated (Avalara's number) — an auditable over/under-collection delta.
  • POS offline fallback (Tax Content API: daily rate/rule tables per location) is a documented option but real work (thresholds, caps, holiday windows implemented client-side) — future phase, not v1.

Monitoring

  • status.avalara.com is the status surface; incidents route to Slack (status-page webhook/bridge ticket).
  • No published SLA/latency/RPS numbers; the one documented limit is concurrency (error 1723). Treat sustained 1723s as a signal to widen the debounce window.
  • Every call is in AvalaraCallRecord — the audit and debugging source of truth.
  • Alerting does not depend on the database: emit low-cardinality metrics (result, error category, latency, timeout rate) alongside the record write, so a DB outage or slow write can't hide an Avalara service failure.
