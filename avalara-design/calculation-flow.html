Plantiful · Sales Tax v2 (Avalara +)

Calculation flow

When we call Avalara, how we batch those calls, and what the payload looks like.

Where calls hook in

Surface Trigger
Sales order form / detail page Tax-basis changes (below), via the flush/debounce model
Draft → quote → order conversion Immediate recalc
POS At checkout advance only — never while building the cart
Online orders Checkout page, on contents/delivery-address change; persisted tax = displayed tax

Tax-basis changes (each is a trigger): line added/removed; line quantity or price change; delivery/pickup address change; summary line change (shipping, drop charge, fee, discount, additional charge); tax effective date change (invoice date, or ship date when it's the fallback — a date shift can cross a rate change); per-line classification change. Modal edit surfaces count — add-line-item, update-line-item, shipment details, and shipment pricing modals are where detail-page changes actually happen.

Flush / debounce model

Avalara bills per call and expects ~3–5 calls per order across its life. Two trigger classes:

  • Full order update (bulk save, order-level edit flow) → fire immediately, flushing the calculation window.
  • Single atomic operation (one line edit, one field change) → accumulate into the calculation window; fire once it settles (debounce).
  • User flush affordance: a "recalculate tax now" action in the UI flushes the window on demand — nobody waits on a timer when they want the number.

Flush concurrency: single-flight lock

Flushes must be serialized — a manual flush racing the debounce timer, two users on the same order, or a trigger landing mid-calculation must not produce overlapping Avalara calls (each costs quota, and Avalara throttles concurrency — error 1723). The analog is the payments mutex (processingPaymentLock: atomic compare-and-set on the shipment row, explicit unlock), adapted for tax:

  • Single-flight + coalesce — a trigger arriving while a calculation holds the lock marks the window dirty and fires exactly one follow-up recalc on release; N triggers during flight collapse to one call. Unlike payments, a competing flush never errors — blocking the user is worse than waiting.
  • Latest-wins guard — each dispatch is stamped with the tax-basis version it was computed from; responses whose version is no longer current are discarded, so a slow in-flight response can't overwrite a fresher result.
  • Crash-safe — the lock expires after a timeout so a wedged holder can't freeze tax recalc on an order indefinitely.

The window was chosen from data, not intuition. A 30-day analysis of production sales-order edit behavior (2026-08-04, read-only prd; tax-basis event types from sales-activity tracking) found 10,497 edits across 3,023 orders ≈ 3.5 edits per order — already inside Avalara's ~3–5 calls-per-order budget with no debounce at all, so the window is an optimization, not a cost-safety requirement. The modal inter-edit gap is 10–30s (2,199 of 7,474 gaps); within-session (<30 min) median 35s, p75 ≈ 101s, p90 ≈ 337s.

Cost-avoidance pre-checks (before any call)

  1. Org entitlement on + org auto-calc setting on — else legacy manual-rate behavior.
  2. Destination state registered (per the org's registration config) — else apply $0 locally and skip the billable call (Avalara would return $0 anyway via nexus).
  3. Exempt customer + exempt-tracking setting off — skip the call and apply $0 locally only when the order has no taxable-classification lines. Partial exemption means an exempt customer can still owe tax on non-qualifying lines (ag-exempt customer buying hard goods), so any order containing a taxable line goes to Avalara regardless of the tracking setting — otherwise mixed orders under-collect. (Setting on: send exempt orders too, so the per-jurisdiction exempt breakdown gets recorded.) Cover the mixed-order case with a test.

Payload assembly

  • companyCode — from the org's foundation record.
  • docCode — scheme pending the uniqueness verification (per-company vs per-company+DocType vs per docCode+customerCode). Prefer the human-matchable shipment name + customer code if the verified key allows; otherwise a company-unique identifier (shipment external ID).
  • date — tax effective date: invoice date, ship date fallback. Calendar-day semantics, timezone-insensitive.
  • customerCode — Plantiful customer ID.
  • Addresses:
    • Delivery: header shipFrom = fulfilling location, shipTo = delivery address.
    • Pickup / POS: the facility's location code plus ship-to = ship-from = the facility address (facilities registered per company via CreateLocations).
  • Per line: number, itemCode, description, quantity, amount (extended, net — see below), taxCode from the item's classification. Send real tax codes always; no NT short-circuit.
  • Exempt customers: header entityUseCode from the exemption-reason mapping; exemptNo carries the certificate number only when exemption is intended — any value in that field force-exempts the transaction.
  • Summary lines: each shipping / drop charge / additional charge / fee / late fee is its own line with its configured tax code (freight code varies by ownership-transfer point: own-truck vs common-carrier).

Net-amount distribution (discounts & credits)

We send Avalara net information — line amounts with discounts and credits already applied ($10 item at 10% discount ⇒ send $9). This is Avalara's recommendation: the customer owes tax on what they actually pay. Shipment-level discounts and credits don't map to any single line, so a dedicated util distributes them down to line amounts — layered on top of existing line-level discounts — with deterministic rounding: distributed amounts sum exactly to shipment totals, remainder cents assigned by a stable rule, property-tested. 

// Distribute a shipment-level discount/credit down to its lines,
// producing the net per-line amounts sent to Avalara.
function distributeToLines(lines, shipmentReduction):
  eligible = lines.filter(line => line.discountable)   // discountable flag gates shipment-level discounts
  base     = sum(eligible, line => line.extendedAmount) // extended = qty × price, line-level discounts already applied

  distributed = 0
  for line in eligible.sortBy(stableKey):               // stable order ⇒ deterministic rounding
    share          = roundToCent(shipmentReduction * line.extendedAmount / base)
    line.netAmount = line.extendedAmount - share
    distributed   += share

  // remainder cents from rounding land on the last eligible line (stable rule)
  eligible.last.netAmount -= (shipmentReduction - distributed)

  // invariant (property-tested): sum(netAmount) === sum(extendedAmount) - shipmentReduction

// Example — $10.00 line + $5.00 line, $1.50 shipment discount:
//   $10.00 line: share $1.00 → net $9.00 sent to Avalara
//   $5.00 line:  share $0.50 → net $4.50 sent to Avalara
//   nets sum to $13.50 = $15.00 - $1.50 exactly; no drift vs the order total

Exception: third-party/manufacturer-reimbursed coupons go as a negative line with tax code OC030000 — the customer is taxed on the pre-coupon base because the seller is made whole.

Response handling

  • Use Avalara's returned dollar amounts verbatim — never recompute from rates (rounding drift vs QuickBooks is the failure mode).
  • Raw request/response → AvalaraCallRecord. Structured per-shipment, per-jurisdiction breakdown (taxable / non-taxable / exempt / collected) is parsed from the stored response.
  • Zero-tax display logic: responses distinguish taxableAmount vs exemptAmount (no-nexus and NOMAD-state results report the full amount as exempt) — enough to explain why a line shows $0.
